### 【修正-1】スマホ入力時に画面が拡大したまま戻らない（修正依頼 No.1, No.24）

- 原文①(No.1): 「入力画面を開いたら拡大したが、入力画面を閉じても拡大が直らなかった。拡大画面が元の入力する前の画面に戻って欲しい」（画面: CON-010 メッセージ入力/送信）
- 原文②(No.24): 「スマホ入力の時、画面が拡大したままになる」（画面: CLI-019 スカウトテンプレート新規作成）
- 関連メモ: ③動作チェック F5-2 にも「画面が拡大されたまま」の記述あり（代理アカウントでのメッセージ送信）。
- 推定原因: iOS Safari は font-size が 16px 未満の input / textarea にフォーカスすると自動ズームする既知挙動。フォーカスを外してもズームが戻らない。
- 調査ポイント:
  1. メッセージ入力欄（`src/components/messaging/` 配下、CON-009 画面下部の入力欄）と、スカウトテンプレートフォーム（CLI-019）の input / textarea の実効 font-size を確認する。
  2. 16px 未満の入力欄をアプリ全体で洗い出す（同種の指摘が他画面でも潜在している可能性が高い）。
- 修正方針の候補: 入力系要素の font-size を 16px 以上に統一（Tailwind の text-base 適用 or CSS 一括指定）。viewport meta の `maximum-scale=1` はアクセシビリティ上避けたい。全画面に効くグローバル対処と影響範囲を提示すること。

### 【修正-2】案件検索を開くとキーワード欄に自動フォーカスされる（修正依頼 No.21）

- 原文: 「検索条件を開いたのと同時に、キーワード入力に選択されていて、手間です」（画面: CON-002 募集案件一覧 /jobs/search、③動作チェック B1-1）
- 推定原因: 検索条件パネルのキーワード input に autoFocus 指定。スマホではフォーカスと同時にキーボードが開き、【修正-1】のズームも誘発するため体感が悪い。
- 調査ポイント: `/jobs/search` の検索フォームコンポーネントの autoFocus 指定箇所を特定。他の一覧検索（発注者一覧・職人一覧・応募履歴等）にも同じ実装がないか確認。
- 修正方針の候補: autoFocus の削除。

### 【修正-3】お気に入り(♡)の解除が一覧に即反映されない（修正依頼 No.22）

- 原文: 「マイページまで戻らないと反映されない」（③動作チェック B3-3: マイリストで♡を外す → マイリストから消えるはずが消えない）
- 推定原因: ♡トグルの Server Action 後の `revalidatePath` 漏れ、または Router Cache が残っていて一覧の再取得が走らない。楽観的UI の状態とサーバ状態の不整合の可能性もある。
- 調査ポイント:
  1. favorites のトグル処理（Server Action）と、マイリスト画面（CON-007 /favorites）・案件一覧・発注者一覧の♡ボタン実装を確認。
  2. どの画面で♡を外した場合に、どの画面への反映が遅れるのかを整理（クライアントの記載は「マイリスト上で外してもその場で消えない」とも「一覧で外してもマイリストに反映されない」とも読める）。
- 修正方針の候補: revalidatePath / revalidateTag の追加、またはクライアント側 state での即時除去。

### 【確認-2】求人を削除できず、退会もできない（修正依頼 No.8）

- 原文: 「現場掲載で、掲載した求人を削除できず、退会もできなくなる」
- 仕様の前提:
  - 案件に「削除」機能はなく、ステータス遷移は draft → open → closed のみ（`.kiro/specs/job-posting/requirements.md`）。closed への変更が「掲載終了」。
  - 退会は進行中案件があるとブロックされる仕様（COM-006）。
- 調査ポイント:
  1. 退会ブロックの判定ロジック（withdrawal のバリデーション）を確認し、**何が「進行中」と判定されるか**を確定する: open 案件の存在／status='accepted' の応募の存在／closed 案件はブロック対象か。
  2. 「案件を closed にしても退会できない」ケースが成立するかをコードで確認する。成立するなら、その状態から退会に到達する手順が存在するか（例: accepted 応募の完了報告が必要だが、評価入力期間外で報告できない等の**デッドロック**がないか）を検証する。
  3. クライアントのアカウントの実データ（案件・応募のステータス）を SELECT で確認し、当時何にブロックされたかを特定する。
- 判定の観点: 削除機能がないこと自体は仕様。デッドロック（どの操作をしても退会に到達できない状態）が存在するなら不具合として報告。

## 成果物の形式

各項目について、以下の4点をMarkdownの表または箇条書きで報告すること。

1. 判定: (A) 勘違い（仕様通り） / (B) 不具合 / (C) 仕様だが改善余地あり。
2. 根拠: 該当コードのファイルパス・行、参照した仕様書、DBで確認した実データの内容。
3. (B)の場合: 原因、修正方針、影響範囲、概算工数。
4. (A)(C)の場合: クライアントへ返す説明文の下書き（ITリテラシーが低い相手向けに、専門用語を避けた平易な文章で）。
