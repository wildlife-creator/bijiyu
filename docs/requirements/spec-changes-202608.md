## 2. 変更内容の詳細

### 2.1 支払い関連

#### (1) 銀行振込の追加（月払い・年払い共通）

決済はアプリ外。アプリは申込み受付・状態管理・有効化のみを担う。

フロー:

1. ユーザーがアプリ上で「銀行振込で申し込む」を実行（プラン or オプション）。
2. アプリが申込みレコードを「申込受付」状態で作成。
3. メール自動送信（2通）:
   - ユーザー宛「運営から請求書をお送りします」
   - 運営宛「請求書を送付してください」（申込者情報・プラン/オプション・金額を記載）
4. 運営が請求書をユーザーへ直接送付（アプリ外）。
5. ユーザーが入金（アプリ外）。
6. 運営が管理画面でユーザーを検索し、該当プラン / オプションで有効化。
   - プラン: 有料会員フラグ ON ＋ 有効期限セット ＋ ユーザー宛「プランのお申し込みを承りました」メール（既存テンプレ流用）
   - オプション: option_subscriptions を active で作成 ＋ ユーザー宛オプション有効化メール（Stripe 購入時の既存テンプレ流用）

メールの新規作成は申込み時の2種（ユーザー宛 / 運営宛）のみ。プラン・オプション共用テンプレとし、対象名と金額を差し込む。

申込みレコードの状態遷移: 申込受付 → 請求書送付済 → 入金確認済 / 取消

期限管理（D3）:
- 期限が来ても自動では停止しない。管理画面で手動更新。
- 管理画面一覧に「期限間近」「期限切れ」バッジを表示。
- 期限30日前と当日に運営宛通知メールを送信。

#### (2) 年払いの追加

- 銀行振込: 上記 (1) のフロー。
- Stripe: 年額 Price を4プラン分追加（計8 Price 構成）。プラン選択画面に「月払い / 年払い」切替 UI を追加。
- サイクル切替ルール:
  - 月払い → 年払い: 即時切替（アップグレード扱い）
  - 年払い → 月払い: 期間終了時に切替（ダウングレード扱い）
- Stripe 月払い会員 → 銀行振込年払い: 現期間終了日を開始日として運営が有効化（D8）。

#### (3) プラン変更時の画面表示

| 操作 | 画面 |
|---|---|
| アップグレード | Stripe ホスト画面（billing portal deep link: `subscription_update_confirm`）。変更後プラン・日割り差額・次回請求を Stripe が表示。決済失敗・3Dセキュアも Stripe 側で処理 |
| ダウングレード | 既存のアプリ内確認ダイアログを維持（期末適用の予約方式のため）。適用日と次回課金額は表示済み |
| 銀行振込会員 | 管理画面での手動対応（Stripe 上にサブスクが存在しないため） |

#### (4) メール送信（プラン変更まわり）

現状の送信内容:

| タイミング | 送信元 | 件名 |
|---|---|---|
| アップグレード直後 | ビジ友 | 【ビジ友】プラン変更を承りました |
| ダウングレード予約直後 | ビジ友 | 【ビジ友】プラン変更を承りました（適用開始日つき） |
| ダウングレード期末適用時 | ビジ友 | 【ビジ友】プラン変更を承りました |
| Stripe 領収書 | Stripe | ダッシュボード設定次第 |

改修時の対応事項:
- ダウングレード「予約時」と「適用時」の件名が同一のため、適用時を「プラン変更が完了しました」等に分離する。
- アップグレードを Stripe ホスト画面経由に変えると送信経路が Webhook フォールバックに切り替わるため、発火確認を実装時に行う。
- 銀行振込の有効化時メール（新設、既存「お申し込みを承りました」テンプレ流用）。
- 銀行振込の申込み時メール2種（新設、動画オプションの「ユーザー受付＋運営通知」ペアのパターンを流用）。

### 2.3 動画関連

#### (1) MP4 直接アップロード

- インフラ: Cloudflare Stream（技術調査済み: docs/research/video-file-upload-study.md）。
- 方式: Direct Creator Upload（ブラウザ → Cloudflare 直接、TUS 対応。Vercel の 4.5MB 制限を回避）。
- 操作者: 管理画面（ADM-010 / ADM-010B）のみ。ドラッグ＆ドロップ UI・進捗バー・二重送信防止を追加。
- 費用目安: 月10ドル程度（100本・月5,000再生想定）。

#### (2) 複数動画・掲載場所の管理

- 現行の1カラム1本構造（users.video_url / client_profiles.workplace_video_url）を廃し、動画テーブルを新設。
- システムは動画の「種別」を持たない。管理側が「どこに載せるか」を制御する方式とする。
  - カラム案: 掲載先ユーザー ID、掲載場所（職人詳細ページ / 発注者詳細ページ など）、表示順、Cloudflare 動画 ID（または埋込 URL）、管理用ラベル（任意テキスト）。
  - 管理用ラベルは管理一覧での見分け用（例: 「職場紹介」「SNS用」）。自由入力のため、動画の種類が増えても改修不要。
- 「スキル動画」「職場紹介動画」「公式SNS用動画」の呼び分けは、料金表・案内上の商品名として維持する（システムとは切り離す）。
- ユーザー撮影プランの成果物も、編集後に管理側が掲載場所を選んで登録する（同じ仕組みに載る）。
- 本数上限なし（D4）。表示 UI は3本程度想定のデザイン。

#### (3) 動画掲載枠の全ユーザー解放

- オプション購入有無による表示ゲートを撤廃し、全ユーザーのページに動画枠を表示可能にする。
- 掲載作業はすべて管理運営側が実施。

#### (4) 新オプション: ユーザー撮影プラン

- ビジ友指定の構成に沿ってユーザーが撮影 → 素材をメールで運営へ送付 → ビジ友側で編集・掲載。
- アプリ側の実装は購入導線のみ（素材授受はアプリ外）。
- 決済: Stripe（一括払い機構は実装済み）＋ 銀行振込（2.1(1) のフロー）。

### 2.4 管理運営アカウント

- 最上位プラン相当の一般ユーザー（名称「管理運営」等）として登録。メッセージ機能の大規模改修は行わない。
- users に非表示フラグを追加し、発注者一覧・職人一覧・検索から除外。
- 課金は手動サブスク行で「支払い済み」扱い（実際の支払いなし。D10）。
- 用途: ①仕事の少ない職人を発注者へ提案 ②求人が集まらない案件を職人へ提案。
- 補足: メッセージ基盤は identity ペア化済みで、発注者⇔発注者・受注者⇔受注者のスレッドが DB レベルで成立する。新規スレッド開始の入口導線のみ軽微な追加が必要。

### 2.5 一覧・並び順

#### (1) デフォルト並び順

- 発注者一覧: ハイエンド → プレミアム → その他。各グループ内は新着順。
- 案件一覧（おすすめ順）: ①急募オプション ②ハイエンド ③プレミアム → その他。
- 実装メモ: 現行は新着順のみ（案件は急募→新着が実装済み）。プランランクでの並べ替えには、一覧クエリからプラン情報を引ける仕組み（ビュー化 or ランク列の非正規化）が必要。

#### (2) 並べ替え UI のプルダウン化

### 2.6 補償オプションの取り下げ（今回の修正完了後に実施）

背景: 補償は保険会社との別契約に切り出す方針。クライアントが保険業の免許を持たないため、アプリ上での販売は保険業法上のリスクがあるとの判断（弁護士 / 保険会社への確認を推奨）。

- 実施タイミング: 今回の修正一式の完了後（フェーズ分離）。
- 実装: 購入 UI（料金プラン画面の補償オプション）を非表示にする。コードは削除せずフラグで制御（将来の復活に備える）。
- お問い合わせの「お問い合わせ内容」に「報酬未払いについて」を追加（未払い発生前の相談も受ける窓口）。
- トラブル報告のカテゴリに「報酬未払い」を追加（発生後の当事者間トラブルの窓口）。両窓口への追加は確定。
- 規約・FAQ・特定商取引法ページの補償記載を修正。
- 既存契約者: いない（補償オプションは未リリース）。契約者移行の対応は不要と確認済み。

考え方:
- P2 が課金系の共通基盤（P3 / P5 / P7 が依存）。
- P4 は課金系と独立のため、体制次第で P2〜P3 と並行可能。
- P5 を P6 より先にするのは、一覧クエリの改修（除外＋並び順）を1回で済ませるため。管理運営アカウントの実登録は P6 完了後。
- 合計目安 29〜45人日（テスト・レビュー込みの粗見積もり。各フェーズ着手時に精緻化）。

実装の進め方（Cursor + Claude Code 前提）:
- 各フェーズ完了時に `.kiro/steering` 配下の仕様ドキュメント（database-schema.md / screen-map.md / product.md 等）を必ず更新する。Claude Code がこれらを前提資料として読むため、古いままだと以降のフェーズで旧仕様に基づくコードが生成される。
- 本ドキュメントをフェーズごとのプロンプトの起点として渡す。
- 各フェーズで既存のテスト3層（vitest / SQL RLS テスト / Playwright E2E）を実行し回帰を検知する。
- フェーズ着手時に受け入れ条件を先に書き出してから実装に入る。

ブランチ運用（3層）:

| 層 | 役割 | 触り方 |
|---|---|---|
| ① クライアント確認用ブランチ（ステージング稼働中） | クライアントが触る場所 | 改修完了まで一切触らない |
| ② 改修まとめブランチ | 完成したフェーズを溜める場所 | ①から1回だけ分岐して作成 |
| ③ 作業ブランチ | 実装する場所 | フェーズごとに②から切り、完了ごとに②へマージ |

- 流れ: ②から P1 用の③を切る → 実装・テスト → ②へマージ → 次フェーズの③を切る（以下繰り返し）。
- P1〜P8 がすべて②に揃い、クライアント確認が済んだら②を①へマージ。この瞬間までクライアントの画面は変わらない。

DB（Supabase）の扱い（1環境を共有）:
- 「追加のみ」のマイグレーション（新テーブル・新列・新 RPC）は作業中いつ適用してもよい。既存コードからは見えず、クライアントのステージング利用に影響しない。
- 「削除・変更」のマイグレーション（旧動画カラム video_url / workplace_video_url の廃止など）は、①へのマージと同時に適用する（追加 → データ移行 → コード切替 → 後日削除の2段階方式。エリアマスタ改修の前例に倣う）。
- 適用前に必ずローカル（supabase start）で検証する。
- 開発中のテストデータはクライアントのステージング画面にも表示されるため、名前に「テスト」等を明示し、確認後に削除する。
