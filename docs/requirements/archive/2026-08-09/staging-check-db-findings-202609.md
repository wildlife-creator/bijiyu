## No.31【確認-4】発注されたのに「結果待ち」— (A) 勘違いで確定

**根拠データ（Q3）**: クライアント（かずひで氏 = user_id `8f5b6eef...` および相手 `b5146f97...`）の応募 2 件はいずれも `status = accepted`。

| 応募案件 | status | 更新日時 |
|---|---|---|
| 表町電気工事 | accepted | 2026-08-19 04:44 |
| かずひで333 | accepted | 2026-08-19 04:59 |

- データ上 `applied（応募結果待ち）` の応募は、初期シードの 2 件（`cc111111...` / `cc222222...`）のみで、クライアント本人のものではない。
- コード上 `accepted` は CON-011 で「稼働予定」と表示される（`accepted` が「結果待ち」と出る経路は無い）。
- **結論**: アプリは正常。別の応募（初期データ等）を見て「結果待ち」と誤認したもの。説明で解決。

## No.33【確認-5】スカウトの受諾ボタンが出ない — (B) 不具合・実際に発生で確定

**根拠データ（Q4）**: 最新のスカウト（`750a3dcc...`、2026-08-19、案件「かずひで　なにもの？」）は **`side1_is_org = true` かつ `side2_is_org = true`**（送信側・受信側とも組織 identity）。

- これは調査で特定した不具合条件「受信側が組織 identity だと受諾/辞退ボタンが表示されず、サーバー側でも応答が拒否される」に完全一致。
- Q4 の他のスカウトはすべて `side2_is_org = false`（受信側が個人）で正常に応答できている。法人同士のこの 1 件だけが該当。
- クライアントは法人アカウント同士でスカウトをテストしたため、ボタンが出なかった。
- **結論**: 実在する不具合。修正-確認-5(1)（受信者判定を「送信者の反対側の participant」に変更、工数 1 日）を実施すべき。

## No.8【確認-2】退会できない — (B) デッドロック実在・到達済みで確定

**根拠データ（Q1・Q2・Q3）**: クライアント `8f5b6eef...`（かずひで氏）は `accepted_as_client = 1`・`accepted_as_contractor = 1`（発注者・受注者の両側で発注済み応募を保有）。相手 `b5146f97...` も同様。

該当する accepted 応募と案件の稼働終了日（Q2/Q3）:

| 応募案件 | first_work_date | work_end_date | 完了報告の期限（+5日） | 現在(9/7)時点 |
|---|---|---|---|---|
| 表町電気工事 | 2026-08-21 | 2026-08-24 | 2026-08-29 | **期限切れ** |
| かずひで333 | 2026-08-20 | 2026-08-19 | 2026-08-24 | **期限切れ** |

- 両案件とも `status = closed`（掲載終了済み）。それでも `accepted` の応募が残るため、退会ガード 2「受注者が作業中の案件がある」に該当し退会がブロックされる。
- 完了報告で `accepted` を解消できる期間（稼働終了日 +5 日）はすでに経過。受注者キャンセル（初回稼働日 5 日前まで）・運営の発注取消（初回稼働日前日まで）も期限切れ。
- **結論**: 「誰も画面から解消できず退会が永久にブロックされる」デッドロックに実際に到達済み。これが No.8 の正体。修正-確認-2（運営が期限切れ accepted を完了/取消にできる ADM-014 操作の追加、工数 1〜1.5 日）が必要。

**補足**: 本番リリース前に、このデッドロック状態のテストデータをどう解消するかは別途対応が必要（運営操作の実装後に解消 or DB で直接補正）。

## No.20【確認-3】本人確認・プロフィール画像 — 現データに WebP 無し（未発生）

**根拠データ（Q6）**: 全 21 件の本人確認レコードの書類拡張子・アバター拡張子を確認。

- 書類（doc1/doc2）は `.png` / `.jpeg` / `.jpg` / `.pdf` のみ。**`.webp` は 0 件**。
- `avatar_ext` は全件 null（このクエリで取得した本人確認保有ユーザーはアバター未設定）。
- **結論**: 調査で特定した「WebP はアバター保存時に弾かれる」不具合は、現データでは誰もまだ踏んでいない（未発生）。予防修正（`AVATAR_PATH_EXTENSIONS` に webp 追加、工数 0.25 日）の価値はあるが、クライアントの「反映されない」の直接原因とは断定できない。
- **要ヒアリング**: No.20 は起票の画面 ID（A4-3 メールアドレス変更）と内容も食い違っている。クライアントに「どの画面で・何の画像が・どう反映されなかったか」を具体的に確認する必要がある。それまで判定は保留（暫定 (C)）。

## F4-1【確認-16】組織スレッド — (A) 確定

**根拠データ（Q5）**: `thread_type = message` かつ組織 ID を持つスレッドが複数存在（例 `510a7e9c...` は organization_1/2 とも同一組織）。RLS で同組織メンバー全員に開放される仕様どおり。組織 ID が NULL のスレッド（`b92a9dec...` 等）は個人間のやり取りで、これは全員には見えない（昇格前スレッドの仕様と整合）。

- **結論**: 仕様どおり。見つけ方（マイページ →「メッセージ・スカウト」）の案内で解決。
