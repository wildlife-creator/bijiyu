## 進め方（厳守）

### フェーズ 1: 現状の再確認・再現（コードを変更しない）

各項目について以下を行い、**まとめて報告する**（この時点では実装しない）:

1. 前提資料に書かれた原因・該当ファイルが、**現在のコードでも正しいか**を確認する。パス・行番号がずれていれば現在地を示す。
2. 原因が変わっていた/すでに直っていた場合はその旨を報告する。
3. 可能なものは再現手順を確認する（ローカル起動 or テストコードで）。
4. 各項目に「再確認の結論（原因は前回どおり／要修正／すでに解消済み）」を付ける。

### フェーズ 2: 修正方針の提示（人間の承認待ち）

フェーズ 1 の結果をもとに、各項目の**修正方針・変更するファイル・影響範囲・テスト方針・工数**を提示する。**ここで一度止まり、人間の承認を待つ。** 承認された項目だけ実装に進む。

### フェーズ 3: 実装・テスト

承認された項目のみ実装する。以下を守る:

- ブランチ運用（`spec-changes-202608.md` §5）に従う。**クライアント確認用ブランチ（ステージング稼働中）は触らない。** ②改修まとめブランチから作業ブランチを切る。
- 1 項目ずつ、またはグループ単位でコミットし、何を直したか分かるコミットメッセージにする。
- 既存のテスト 3 層（vitest / SQL RLS テスト / Playwright E2E）を実行し回帰を確認する。修正に対応するテストを追加する。
- DB は追加のみのマイグレーションに留める（削除・変更は①マージ時。§5 の「DB の扱い」に従う）。
- SELECT 以外で本番/ステージングのクライアントデータを変更しない。

## 修正対象 9 件

各項目の「前回の見立て」は出発点。フェーズ 1 で検証すること。

### 【高】1. スカウトの受諾/辞退ボタンが出ない（指摘 No.33 ／ 確認-5）

- 症状: 法人プランの会員が職人としてスカウトを受けると、「受ける/断る」ボタンが表示されず、サーバー側でも応答が拒否される。
- DB 確認: 該当スカウト（thread の送信側・受信側が両方 organization identity）が実在。クライアントが実際に踏んだと確定。
- 前回の見立て: 受信者判定が「identity が null の側」を受注者と決め打ちしている。`messages/[threadId]/page.tsx`（ボタン表示条件）と `messages/[threadId]/actions.ts`（応答処理）の 2 箇所。
- 前回の修正方針: 受信者判定を「スカウトメッセージの送信者の反対側の participant」に変更し、2 箇所を同じ判定関数に統一。
- フェーズ 1 で確認: 現在のボタン表示条件と応答権限チェックのロジック。組織 identity のスレッドで受注者側がどう判定されているか。

### 【高】2. 退会できなくなる「詰み」状態（指摘 No.8 ／ 確認-2）

- 症状: 発注済み（accepted）の応募が残ると退会がブロックされる。それを解消する完了報告・キャンセル・運営取消がすべて期限付きで、稼働終了日+5日を過ぎると誰も解消できず退会が永久にブロックされる。
- DB 確認: クライアントのアカウントがこの状態に到達済み（期限切れの accepted 応募が残存）。
- 前回の見立て: 退会ガードは `src/lib/withdrawal/execute.ts`。accepted 解消経路は完了報告（初回稼働日〜稼働終了日+5日）・受注者キャンセル（初回稼働日5日前まで）・運営取消（初回稼働日前日まで）の3つで、すべて期限切れ後は不可。
- 前回の修正方針:
  1. 運営（ADM-014）に、期限切れ accepted を「完了扱い」または「取消」にできる操作を追加（監査ログ付き）。← デッドロックの根治
  2. 退会エラーメッセージに対象案件名と「期限切れの場合はお問い合わせへ」の導線を追加。
- フェーズ 1 で確認: 退会ガードの現在の条件。ADM-014 の既存操作。**あわせて、ステージングに現存する詰み状態のテストデータをどう解消するかも方針に含める。**
- 補足: 受注者が「結果待ち（applied）」を自分で取り下げる機能が無い件（FAQ と不整合）も関連。フェーズ 2 で対応要否を判断。

### 【高】3. スマホで入力欄が拡大したまま戻らない（指摘 No.1・No.24 ／ 修正-1）

- 症状: iOS Safari で、文字サイズ 16px 未満の入力欄にフォーカスすると画面が自動拡大し、戻らない。
- 前回の見立て: 共通部品を使わず独自にサイズ指定した入力欄が 3 ファイル・5 箇所（メッセージ入力欄、スカウトテンプレートフォーム、職種・資格・スキルの検索コンボボックス）。
- 前回の修正方針: 該当箇所に `text-base md:<現行サイズ>` を付け、スマホでのみ 16px にする（PC の見た目は不変）。再発防止で design-rule に注意書き。
- フェーズ 1 で確認: 16px 未満の入力欄をアプリ全体で洗い直す（前回の 3 ファイル以外にもないか）。

### 【高】4. 検索条件を開くとキーワード欄に自動フォーカス（指摘 No.21 ／ 修正-2）

- 症状: 案件検索などで検索条件パネルを開くと、キーワード入力欄が自動選択されキーボードが立ち上がる。
- 前回の見立て: 検索パネルが Radix Dialog ベースの共通 Sheet（`search-filter-sheet.tsx`）で、Dialog のデフォルトで先頭要素へ自動フォーカスする。CON-002 / CON-005 / CLI-005 の 3 画面が該当。
- 前回の修正方針: `<SheetContent>` に `onOpenAutoFocus={(e) => e.preventDefault()}` を追加（3 画面に一括で効く）。
- フェーズ 1 で確認: 現在の Sheet 実装と、3 画面が同じ部品を使っているか。

### 【高】5. お気に入り(♡)解除がマイリストに即反映されない（指摘 No.22 ／ 修正-3）

- 症状: マイリスト画面でハートを外しても、その場でカードが消えず、開き直すと消えている。
- 前回の見立て: ハートボタンが自分の見た目を切り替えるだけで、解除後に一覧を更新する仕組みが無い。マイリスト画面が Server Component でカードを固定表示。DB 側の削除は正常。
- 前回の修正方針: 解除成功時に `router.refresh()`（マイリスト画面でのみ有効化）、または一覧をクライアント部品化して即時除去。`toggleFavoriteAction` に `revalidatePath("/favorites")` も追加。
- フェーズ 1 で確認: 現在のお気に入りトグルとマイリスト画面の実装。

### 【中】6. 管理画面の「もどる」ボタンの飛び先間違い（自由チェック No.35・No.37/38 ／ 確認-6〜15）

- 症状: 管理画面で画面内「もどる」を押すと、来た画面ではなく一覧やトップに飛ぶ。
- 前回の見立て:
  - No.35: 発注者詳細の「応募◯件」→ 応募一覧の検索フォームが URL を組み直す際に `backTo` を落とす。
  - No.37/38: ユーザー詳細の「発注者詳細」リンクだけ `backTo` を引き継いでいない。
- 前回の修正方針: リンクに `backTo` を付与／検索フォームで `backTo` を維持。
- フェーズ 1 で確認: admin の `backTo` リレー方式の現状と、該当リンクの引き継ぎ状況。

### 【中】7. 管理画面の検索欄がブラウザ戻りで元に戻らない（自由チェック No.40 ／ 確認-6〜15）

- 症状: 管理画面で検索した後にブラウザの「戻る」を押すと、検索欄の表示が検索後の値のまま残る。
- 前回の見立て: 検索フォームの入力値が「マウント時に一度だけ URL から写す」実装で、戻るで URL が変わっても表示が追従しない。users / applications / contacts / job-inquiries / trouble-reports の検索フォームが同型。
- 前回の修正方針: 「URL の値をそのまま表示に使う」形に揃える（useEffect 同期 or key による再マウント）。
- フェーズ 1 で確認: 各検索フォームの現状。
- 補足: 同じブラウザ戻り指摘のうち No.36・42・43・34・39 は「Web アプリの標準挙動」または「要実機再現」で、不具合と確定していない。これらは修正対象外だが、フェーズ 1 で余力があれば実機再現条件だけ切り分けて報告する（実装はしない）。

### 【中】8. プロフィール写真が WebP 形式だと保存に失敗（確認-3(b)）

- 症状: WebP 形式の画像をプロフィール写真に選ぶと、Storage 保存は成功するのに DB のパス更新で弾かれ、写真が反映されない。
- DB 確認: 現データに WebP は 0 件（まだ誰も踏んでいない）。予防的修正。
- 前回の見立て: アップロード後にパスを保存する処理が使う `AVATAR_PATH_EXTENSIONS` に webp が含まれていない（書類用は対応済みでアバター側だけ漏れ）。
- 前回の修正方針: `AVATAR_PATH_EXTENSIONS` に `"webp"` を追加、関連の MIME/拡張子定数も揃える。
- フェーズ 1 で確認: 現在のアバター保存バリデーションと、案内文言（「WebP 対応」と表示しているか）の整合。

### 【中】9. 本人確認書類の画像がまれに表示できない（確認-3(a)）

- 症状: 管理画面で本人確認書類の画像がまれに「表示できません」となる。
- 前回の見立て: 署名付き URL の生成が一時的に失敗すると null を返し、画面にリトライ導線が無い。開き直すと直る。構造的なバグは見つからず、この間欠要因のみ。
- 前回の修正方針: 署名 URL 生成失敗時に 1 回自動リトライ、または「再読み込み」ボタンを表示。
- フェーズ 1 で確認: 署名 URL 生成箇所と管理画面の書類表示部品の現状。
- 補足: クライアントの No.20「画像が反映されない」は、この 9 番か 8 番か別要因か未確定。実装しつつ、クライアントへの状況ヒアリングは別途行う。
